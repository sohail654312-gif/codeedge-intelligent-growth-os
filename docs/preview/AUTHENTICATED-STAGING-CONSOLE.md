# Authenticated read-only staging console

Child of Preview PR #8 (`fb5e5807cd1b8ed2acd96f05ddb9ddc4efd2c285`). The released Codeedge wordmark, navy dashboard, navigation, dialogs, focus handling and responsive layout remain shared with Demo. `/` is the synthetic Demo/Sandbox; `/staging` loads a separate authenticated entry point. A staging failure clears all visible observations; no demo import or fallback runs in staging.

## Identity and current access

The server uses the released Business OS authentication pattern: Supabase Auth password sign-in and the provider `/auth/v1/user` verification (`getUser` semantics). Identity is never decoded as trusted before the provider verifies the exact access token and confirms the user. The verified subject must match the provider user, `session_id` must be a UUID, and token expiry/issued-at must be valid. Browser JSON supports only email/password for sign-in and an independently authorized workspace selector for reads. Actor/role/membership/verification claims are rejected.

The session cookie is `__Secure-cigo_staging`, HttpOnly, Secure, SameSite=Strict, scoped to `/api/staging`, and capped at 30 minutes. There is no browser token storage, refresh token, signup, recovery email or auto-refresh. Logout revokes the provider's local session and clears the cookie; a provider outage clears the cookie and reports that revocation was not confirmed. A stolen expired token cannot extend the server-enforced 30-minute limit.

`src/staging/session.ts` composes `TrustedIdentityResolver`, `TrustedMembershipResolver`, `MembershipAuthority` and `requireWorkspaceIdentity`; existing contracts are unchanged. Each HTTP request verifies the exact provider token at entry and again before disclosure; request-local verification avoids duplicate provider calls while every authorization queries current database membership/session state. The dedicated gateway can execute three narrowly scoped server functions only. Those projections require an actual `auth.sessions` row, matching actor/session, active Business OS business/membership, and an active, non-revoked, unexpired additional staging grant. Session `not_after` and creation +30 minutes apply independently of browser cookie lifetime. OWNER/ADMIN/VIEWER are permitted; MEMBER/staff is denied. Version includes staging grant and current Business OS membership/business timestamps. Actor/session/version/role changes during a request invalidate its earlier authority.

These functions are private server projections, not Supabase browser RPCs: PUBLIC/anon/authenticated receive no EXECUTE, and the gateway receives no direct membership/user/session table permissions. Their SECURITY DEFINER owner reads the private provider and Business OS tables using a fixed `pg_catalog` search path. They do not infer identity from a SQL GUC or caller JWT; verified identity is supplied exclusively by the server-held provider verifier. No owner/service_role credential is installed in the application.

## Read, provenance, truth and presentation

The request path is: verified session → current workspace authorization → server-selected tenant pool/read configuration → existing `BusinessOsHttpReadModelPort`/`BusinessOsReadModelReader` → protected Business OS v1 projection → existing structural validation → exact durable source receipt → `ingestWithTrustedIdentity` and tenant-bound `PostgresEvidenceStore` → evidence ledger → `validateTruthRecord` → request-scoped BusinessMemory → `analyzeKnowledge`/`analyzeBusinessMetrics` → explicit presentation DTO.

The original R4/source SQL is reused unchanged; `STAGING-CONSOLE-AUTHORITY.sql` adds only private access/session projections and login throttling. Receipt/evidence issuer logins are distinct, non-owner/non-inheriting/no-BYPASSRLS roles with forced RLS policies fixed to a single synthetic workspace. They have only SELECT/INSERT on immutable CIGO intelligence evidence, audit/intake and source receipt/identity tables, and SELECT-only revocations. No application UPDATE/DELETE/TRUNCATE, role management or Business OS operational writes are granted. The gateway cannot read raw operational or authority tables.

Each nonempty complete page must pass durable exact-record/page receipt checks before intake, truth or memory. Receipts are checked again after analysis for expiry/revocation; session/membership is checked again immediately before DTO return. Missing receipt authority, wrong scope/source/fingerprint, tampering, partial/error pages, conflicts, database outages and current revocations fail closed. Empty pages produce no attested record and never establish a guessed zero metric.

Source provenance `VERIFIED_SOURCE` means only that exact source observations passed durable receipt checks. Semantic evidence stays `UNVERIFIED`; memory is `ANALYSIS` or `ASSUMPTION`, never FACT. HTTP 200 alone cannot bypass these boundaries. Analysis remains non-actionable, with insufficient confidence. Missing cohorts yield no recommendation/review packet; future execution buttons remain disabled.

The safe DTO projects aggregate observations, semantic limitations, source coverage/counts, observation/analysis timestamps, provenance status and unverified memory text. It omits actors, memberships/roles/session IDs, raw records, external customer references, fingerprints, receipt IDs/payloads, database/service credentials and cursor/verification keys. Raw source data never enters a template. HTML is escaped and CSP uses only same-origin resources, with no inline code, third-party fonts or framing.

Only complete, fresh lead projections with valid creation dates support the current UTC-month lead count. Future/stale/partial data suppresses values. Conversion, attendance, unanswered enquiries, revenue aggregates, marketing spend, retention cohorts and capacity remain unavailable when the v1 projection does not establish their exact semantics. Resource availability is not evidence of aggregate availability. Observations are synthetic staging data, visibly distinct from Demo fixtures.

## Bounded requests and error behavior

One page of at most 100 records per each of eight allowlisted resources; no automatic continuation, duplicate background reads or polling. A continuation marks bounded partial coverage rather than a complete aggregate. Adapter timeout is 6 seconds, retries zero; provider verification timeout 6 seconds; connection/query/statement timeouts are bounded. The request composition has a 55-second deadline. All API responses/errors are `private, no-store`, `Vary: Cookie`; no tenant data cache exists. UI request generations discard superseded responses on workspace changes and immediately erase the previous snapshot during loading, logout or failure. Same-origin Origin checks protect POST/DELETE session operations; no CORS access is granted. Login is restricted to staging-authorized synthetic accounts and throttled durably to ten attempts per account per ten minutes.

Only GET session/workspace and GET snapshot plus POST login/DELETE logout exist. No action ports, provider clients, decision approval/execution, CRM/finance mutation, messages/calls/bookings, marketing launch, R7 effects or automations are composed. CIGO receipt/evidence persistence is intelligence storage, not an operational/provider effect.

## Setup and secret handling

Run `npm ci --ignore-scripts`, `npm run staging:build`, and `npm run staging:serve`. The existing Demo commands remain unchanged. The staging server needs `CIGO_STAGING_SERVER_JSON`, installed only in a protected staging server environment. Alternatively, an owner may inject `dist/staging-runtime-private.json` into the private function artifact outside Git; the fixed server path is not selected by browser input and is never copied to static assets. Its fields are: `enabled`, trusted `origin`, `authUrl`, `publishableKey`, `authDatabaseUrl`, CA-pinned `databaseCa`, `workspaces` (server labels and tenant-specific restricted PostgreSQL URLs), `businessOsOrigin`, private deployment-protection cookie, and `readerEnv` with the original Business OS reader/cursor configuration. This value is never generated into browser assets. TLS verifies the Supabase pooler CA and hostname; no insecure TLS option is allowed.

Provision only an explicitly authorized synthetic staging database, never production. Apply the existing R4/source receipt SQL and additive authority SQL as the migration owner; provision reviewed tenant-fixed roles/policies and the three-function gateway grant. Create two synthetic Supabase users with distinct authoritative memberships and expiring staging grants. Keep public signup/recovery disabled in this console; synthetic provisioning must not send mail. Owner provisioning of actual provider accounts is separate from the disposable CI provider fixtures.

The acceptance environment uses the existing dedicated Business OS test project and synthetic workspaces. Accounts, restricted role passwords, protected-preview access and server configuration are retained locally under Windows DPAPI CurrentUser. No secret is committed. Deployment preparation reads only reviewed source and the public static allowlist; server configuration may be injected as the private fixed-path function artifact outside Git when the connector cannot install deployment-specific runtime env and branch-scoped secrets are unavailable on the existing test project's different Git connection. The function includes that private artifact under `dist/**`; the explicit browser build copies only its public eight-file allowlist. Do not publish the private artifact, put it in the static output, change production aliases, change the project Git connection/defaults, or disable Deployment Protection. A dedicated CIGO project with managed branch-scoped secrets remains the preferred owner setup.

## Rotation, revocation, disable and rollback

Rotate server role passwords and Business OS service/cursor credentials through the authorized staging owner; install updated restricted URLs/keyring and redeploy. Retain old cursor keys only for the bounded cursor lifetime, then revoke old read grants. Refresh the protected Business OS share cookie through the legitimate Vercel access tool before its expiry; expire/revoke the old deployment if appropriate. A protection-cookie expiry gives a safe unavailable state, never a protection bypass. Do not print tokens/passwords/configuration in logs or handoff files.

Set `cigo.staging_access.revoked=true` or `active=false`, expire the grant, revoke authoritative Business OS membership, or terminate the matching provider session to deny subsequent requests. Rotate the grant version when updating access. Verify denial with the real synthetic account. Tenant/source receipt revocations are append-only owner operations; application logins cannot issue them.

Disable with server `enabled=false` and redeploy; additionally revoke the two synthetic staging grants/provider sessions and Business OS read grants for a complete owner-operated shutdown. Roll back to the immutable PR #8 Demo artifact or an accepted prior read-only console deployment, preserving evidence history. Do not drop evidence/source tables or alter Business OS operational data as rollback. Delete restricted staging logins/credentials only after active deployments are disabled and ownership reviewed.
